# Runtime verification and declared limits

Workspace witness initialization synchronizes its validated private directory and the installer-owned supervisor home before opening SQLite. Both barriers run again when a failed attempt left the directory behind, and a failure returns `not_sent` before the helper or request write boundary runs. `workspace-witness-durability.test.ts` injects child/parent sync failures, parent replacement and symlink storage, then checks retry and accepted-proof readback. On Linux it uses real directory descriptors and fsync; Windows development tests model those directory syscalls because Windows cannot perform the production directory barrier. These checks establish ordering and failure handling, not physical power-loss behavior of a particular filesystem or storage device.

On Windows, run `tests/runtime/windows-job.test.ts` for real process-tree ownership checks. The built-in PowerShell/.NET controller starts the native root suspended, assigns it to an unnamed non-breakaway Job Object with kill-on-close, and then resumes it. Only the three protocol pipe handles are inherited. Explicit shutdown uses a separate named event so blocked stdin cannot delay cleanup; root exit, owner exit and stdin EOF also terminate the job. Tests cover detached children retaining stdout, root-first exit, blocked input, owner death, controller death and Windows argument quoting. This follows the Windows [Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects) and [handle-list inheritance](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-updateprocthreadattribute) contracts; it does not contain processes deliberately launched through independent external services such as WMI.

## Coverage mapping

Task workflows live in `workflows.ts`, with activity, owner, attachment and complete-history authority retained by `RuntimeService`. Run `tests/runtime/workflows.test.ts` for the focused state, race and persistence regressions, and `tests/runtime/workflows-native.test.ts` for the verified 0.164.0 CLI against a loopback-only Responses fixture. The latter checks persisted queue/goal state across a real process restart, explicit resume, active-turn steering, fork anchors, history-only revert, full export and a separate inline review. No commercial inference or external MCP is involved.

`thread/session` only reads a captured start/resume/fork/settings snapshot and returns `requiresResume:true` when that snapshot is unavailable. Viewing stored history never invokes native resume. `thread/resume` is an explicit mutation, requires the current connection's complete history proof, and may start persisted native work. New conversations capture their native creation settings immediately. Settings writes invalidate the snapshot until a complete native settings notification refreshes it.

Queue entries belong to the native durable store. The official CLI immediately consumes a queue addition when idle and automatically consumes persisted entries on resume; active-turn queue start is rejected. Add/update therefore use the work and complete-history gates. Queue edits that omit attachment IDs retain the original non-text and managed-file inputs; explicit `[]` clears inputs. Accepted or uncertain file references remain pinned even after queue deletion, because an automatic turn may already have consumed them. Goal changes force user provenance. Omitted token budget preserves it, `null` clears it, and pausing/clearing the goal does not interrupt an already running turn. Native owns continuation. Known active goals, armed queues, and bounded continuation readbacks remain visible as active work between turns; failed readback blocks maintenance as unknown.

Forks preserve the native project and defer inherited goal continuation; both source and child require real history hydration before further work. Revert invalidates every connection's history proof and does not restore files. Search windows are explicitly partial and never establish complete history. Search is filtered to the selected project after native paging, so an empty page may still have a next cursor. Agent listings are scoped to the selected ancestor and native cwd, preserve direct-input capability, and cannot manufacture subagent spawn support. Exports preserve structured tool records and fail visibly beyond 8 MiB or 128 pages. Thread settings deliberately exclude arbitrary cwd overrides and deprecated multi-agent/personality aliases; native disabled plugin IDs remain saved metadata, not a capability filter.

## Explicit resource policies

- Native wire: 12 MiB per frame, 64 live request/write slots, 32 MiB reserved request bytes. All writes share one serialized writer. A write callback owns its buffer until completion. Default request deadline is 30 seconds; a deadline after write terminates that protocol epoch. Terminal execution waits for native exit without a request deadline but still consumes one bounded live slot. No automatic native replay or restart occurs.
- Private HTTP: 48 requests and 24 MiB retained request bodies; 8 MiB per body, 15-second request-body timeout. Responses/events retain full content within 12 MiB; overflow is a visible error or disconnect, never silent truncation.
- Private events: four gateway sockets; 16 MiB buffered output cap; 15-second ping interval, unresponsive peers terminated by the following tick. Every socket receives a fresh private `eventChannelId` in its initial state. RPC requests bind that identity in `x-harness-event-channel`; admission, completed request bodies, and the final native write all reject a closed channel, including after another socket connects. Before exposing a browser connection, the gateway registers a new, never-reused owner UUID with `/connect`. Each channel permits 64 active owners, and registration/disconnection bodies are limited to 4 KiB within the same 48-request budget. `/disconnect` revokes an owner before cleanup, so late bodies and queued native writes cannot create terminals afterward. Unknown owners cannot issue RPCs. Closing any channel clears its active owners, history traversals and terminals. Terminal events are delivered only to their owning channel. The gateway consumes transport identities without exposing them to the browser. Browser liveness and registration ordering are enforced at the gateway.
- Prompts: 64 waiting requests, 8 MiB aggregate prompt content, 1 MiB per answer. Native IDs preserve number/string identity. Duplicate native request IDs cannot create another consumable prompt. Approval records are consumed after validation and successful write; epoch loss closes them.
- Activity: 2,048 tracked threads; overflow makes new work unavailable rather than evicting active/unknown work. Ordinary reads never clear an unknown operation.
- History: 100 turns requested per page, 8 MiB/2,000 items in a page, 4,096 UTF-8 bytes per opaque cursor, 128 pages per traversal, 256 traversal contexts. Every returned turn must declare `itemsView:"full"`, including legacy reads. Send and compaction admission require a complete, continuous traversal for that client/thread; only a thread whose creation this epoch witnessed and whose first turn was never accepted or uncertain can skip hydration. The final write rechecks this proof. New first-page reads invalidate old proofs, and stale results cannot restore them after client/gateway disconnection. Disconnection releases traversal capacity even when that client has no terminals. Larger legacy histories explicitly fail; they are not reported complete. Directory pages request at most 100 records. The browser must also preserve already displayed content on an error. The explicit write-classified `thread/resume` route accepts only `threadId` and uses a durable operation receipt. Resuming can restore saved queues or a continuing goal; reading history alone never resumes execution. Configuration changes use separate validated mutations.
- Attachments: eight per turn, 4 MiB each, 128 physical or reserved files/128 MiB total, two-MiB durable metadata, at most 256 thread references per file. Directory iteration stops at 160 entries. Every orphan consumes quota; only recognized upload/temp names older than 24 hours can be collected. Deletion first durably marks a tombstone, and failed unlink continues reserving bytes/count across restart until removal is confirmed. Reads use no-follow/nonblocking descriptors where supported, fstat regular-file/single-link/size/identity checks, bounded reads, post-read identity checks and a persisted SHA-256 digest. A substituted or changed file fails visibly. The authenticated administrator can reuse opaque IDs after tab replacement; terminal ownership remains connection-bound. Referenced and uncertain attachments remain retained. A definitive `not_sent` turn failure releases only that send's newly reserved references; prior durable references and overlapping accepted/uncertain reservations remain pinned. A crash or failed rollback remains conservative. POSIX writes/metadata renames sync the file and directory. Production data files are supervisor-owned 0640 in a 2750 directory readable by the native group; index metadata remains 0600.
- Terminals: two per client, 16 total, 1–500 rows/columns, 64 KiB text per write. The terminal intentionally runs with the native execution account's shell privileges, independent of model sandbox settings. Native output is forwarded as base64 so the browser can maintain a streaming UTF-8 decoder. If disconnect cleanup cannot submit or confirm a terminate request and the terminal has not independently ended, the service closes its entire native epoch once and waits for the shared process cleanup acknowledgement. It does not retry indefinitely or treat a rejected terminate as success; cleanup failure remains visible and requests worker shutdown.
- Effective defaults: one simultaneous dedicated CLI probe, 16 cached results keyed by a SHA-256 hash of canonical effective config/options/cwd, 256 KiB config input budget. The service owns the active probe and its idempotent close waits for both main and probe process cleanup. A config read completing after shutdown cannot create another probe. Production project resolution runs under the native UID through the fixed launcher. The supervisor starts sudo from `/` because native-only projects need not be accessible to it. EOF asks the root-owned launcher to terminate and verify its native process tree; only a zero exit within six seconds acknowledges cleanup. Probe cleanup failure makes the main worker fatal. Production worker failure exits for systemd to kill the entire cgroup before restart. Development uses a separate Unix process group or owned Windows Job Object; uncertain cleanup is an error, never authority to start a replacement CLI.

The production supervisor rejects UID 0 and requires a root-owned, ancestor-protected launcher. Legacy native units permit only the five fixed `app-server`, `catalog-server`, `version`, `resolve-project` and `workspace` modes through sudo. Managed execution policies additionally permit the fixed read-only `identity` mode: startup checks its actual UID, mode, server root authorization and policy revision against the generated unit before starting the app-server. A policy-free compatibility unit can use only the original native worker identity, never root. `catalog-server` accepts exactly one validated enabled-provider identity, not arbitrary command arguments. Configuration-layer rollback can restore the exact earlier policy without `workspace`. Exact earlier policies without `catalog-server` are recognized for upgrade admission or protected journal-bound restoration of prior state; they do not satisfy ordinary final verification or establish the new catalog capability.

The server operator must authorize root before the web administrator can explicitly select it; default execution remains native. The supervisor and gateway stay unprivileged. Root execution deliberately grants host authority, including access to Harness itself, and must not be described as isolated from its control files or credentials. Native and root execution use separate HOME/CODEX_HOME and managed project/worktree roots; mode switching does not copy account credentials or change ownership of the original native home. Attachment read-group selection and supervisor-owned witness storage remain unchanged. The launcher receives no control credentials or extra inherited descriptors and independently loads the provider environment; the supervisor retains provider secrets only for diagnostic redaction. Under native execution, the native account has no IPC group membership and cannot modify supervisor-owned attachment metadata or control sockets. `execution-mode.test.ts` verifies fixed command selection, fail-closed identity mismatch, immutable status and managed-home preparation using local protocol substitutes; actual Linux UID, authorization and service-transaction tests are separate deployment evidence.

## Unverified integrations

The initial local native smoke established Windows CLI/PTY behavior. Each later run establishes only its recorded platform and scope; a native smoke alone does not establish Linux systemd cgroup behavior, interactive browser IME/accessibility, real account/device-code login, commercial provider inference/tools, or real external MCP OAuth/tool calls. Linux isolation evidence belongs to separate integration runs. Unsupported MCP extensions may be declined/canceled but cannot be accepted. Runtime stderr is drained without retention to avoid exporting credentials or prompt content; gateway management diagnostics are a separate subsystem.

A separate isolated migration probe used a checksum-verified official 0.149.0 CLI to generate two real turns against a loopback Responses fixture, then closed its stdin and confirmed natural exit code 0. After backing up and hashing the rollout, the current RuntimeService with official 0.164.0 identified `historyMode: legacy`, returned both turns with full items, and continued a third turn. Configuration bytes stayed unchanged and all native PIDs/listening ports were closed. This verifies that constructed legacy history, not arbitrary user archives or an in-place production migration. Evidence: `verification/audit-evidence/preaudit/runtime-migration.json`.

Official 0.164.0 does not materialize a newly started thread until its first user message. Its `thread/read` works, but `thread/turns/list` rejects before that point. The runtime returns an empty complete history only for a thread whose creation it witnessed in the current epoch and which has never crossed a turn write boundary or emitted turn/started. An arbitrary empty `Thread.turns` array is not such evidence. A pre-message thread's native persistence across a worker restart is not guaranteed by its creation response.

The browser-facing creation operation is therefore `conversation/start`: validate input/attachments/options, create the native thread, then send its first user turn under one durable operation identity. Successful output contains both thread and turn. After creation has succeeded, any first-turn failure is an overall unknown outcome with `phase:first_turn`, `threadId`, `causeCode`, and `causeDelivery`; it is never automatically replayed. A known `not_sent` first turn leaves the created thread idle, instead of claiming unknown live work; an uncertain first turn retains its activity barrier. The raw runtime `thread/start` remains for the internal primitive and no-inference native smoke only.

The gateway records that composite operation's dispatch once, while the worker checks the current browser owner before both native mutations. Revocation after thread creation prevents the first turn and retains the partial-thread outcome above. Attachment Base64 validation uses a bounded decode/canonical round-trip; regressions cover exactly 4 MiB and both adjacent padding lengths, malformed encodings, and over-limit input before storage mutation.

The pre-audit repair regressions cover incomplete and unloaded history, continuous cursors including the empty string, cross-client proof isolation, stale reads and disconnection at the final write boundary, traversal capacity reclamation, definitive versus uncertain first-turn failures, overlapping attachment reservations, and rejected resume overrides. Elicitation decline/cancel and URL confirmation also accept omitted optional `content`/`_meta` as allowed by the official JSON schema; non-null cancellation content is still rejected.

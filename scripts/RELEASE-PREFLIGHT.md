# Release preflight for maintainers

Run the existing affected tests during development, including ordinary/root deployment pairs and the appropriate Windows/Linux native fixtures. A topic branch without a pull request does **not** automatically start GitHub checks: use local targeted verification or `workflow_dispatch` with an explicit reviewed base. `Reviewed checks` runs on pull requests and main pushes, so a topic push with an open PR no longer launches a redundant second matrix. Security checks remain separate; CodeQL findings are not dismissed by this change.

After the user-authorized clean audit gate, create the exact source-bound full-test authorization, commit the candidate and run:

```text
node scripts/release-preflight.mjs --head <candidate-commit> --push-base <previous-head> --pr-base <current-target-head> --authorization-sha256 <exact-authorization-file-sha256> --build
```

Use the pinned Node version from `deploy/common.py`, and install dependencies with the pinned pnpm and `pnpm install --frozen-lockfile --ignore-scripts` first. `--build` invokes the existing TypeScript and Vite entrypoints; it does not install dependencies, fetch credentials, push, create a workflow run, or execute any tests. Its fixed generated output directories `dist` and `web/dist` are rebuilt from empty directories. It refuses substituted output directories or parents.

The preflight:

- Requires the supplied commit to be checked out, and compares every source filename, raw Git blob hash and executable bit with that commit. Untracked/changed source cannot be hidden by a successful prior build or Git's `assume-unchanged` flag.
- Reuses `releaseAuthorization` for the complete current-source authorization, and requires its exact bytes to be committed at the candidate. It never invents audit rounds or silently accepts a stale authorization.
- Reuses `buildCiPlan` for the previous-head push plan and PR merge-base plan. It records both exact file lists and platform targets, and requires the release PR to select the authorized full inventory. The push plan is diagnostic for a topic branch, whose push trigger is disabled; it is not an extra requested CI run.
- Checks local Node, workflow Node pins, pnpm/deployment/package pins, exact CI Python and both official CLI package versions. It checks installed TypeScript/Vite package versions against package.json. This is not a fresh dependency-install or supply-chain integrity proof.
- Writes `.work/release-preflight-build.json` only after successful builds and a second source/commit check, with hashes of every emitted artifact. A later invocation without `--build` requires that source-bound record and identical outputs. Merely finding `dist` is not evidence. Evidence-only commits may reuse a build when the entire source digest and output bytes still match.

The result is `.work/release-preflight.json`. `ready-for-ci` means these preconditions passed; it explicitly says `testsExecuted:false` and `releaseGatePassed:false`. Missing build evidence, wrong pins, stale authorization or source changes return nonzero with `status:blocked`. It does not repeat the complete historical Git-object security scan, which remains a hosted plan-step responsibility. No preflight result substitutes for actual complete CI, skip reconciliation, security review, isolated upgrade acceptance or final deployed verification.

## Lessons behind these checks

The [complete historical failure review](../verification/reports/reviewed-checks-history.md) indexes workflow runs 1–59, including the former Affected checks name: 26 failures and 3 cancellations reviewed separately. Read its cause-specific evidence and remaining limits before selecting tests. This is a fixed historical snapshot, not an automatically refreshed dashboard.

The selector is a manual mapping, not a complete dependency graph. For shared fixtures, search imports, direct construction, `setUp()` composition, instance method replacements and cleanup, then add every actual affected consumer to the targeted plan. Known unmapped edges include control-update fixtures consumed by root configuration/lifecycle tests, root lifecycle setup consumed by candidate-archive tests, execution-mode setup consumed by proxy-transaction tests, and journal-schema fixtures consumed by root journal-recovery tests. Test-only edits and hand-picked targets also do not inherit the full Web partition. Before another candidate, explicitly map each previous failed assertion to its preserved review, repair, consumer checks and actual verification; the preflight does not currently enforce that mapping. Record the root system Python separately from the standard matrix's exact Python pin. These are required manual checks, not claims that the remaining automation gaps have been implemented.

Runtime history changes require tracing every `RuntimeService` history consumer, including indirect callers such as predictions, automation and conversion. In v2.3.3 candidate `historical-commit-005` (Reviewed checks run `41334305304`), the new bounded reader requested `thread/items/list`, but the prediction fixture implemented only turn/timeline listing and silently returned `{}` for the new method. Five prediction cases consequently failed before their intended assertions. The broad selector already included this file; the manually chosen targeted subset omitted it. Before narrowing that subset, inspect every native mock used by history callers and run all affected consumers against the actual pagination contract, including legitimate empty pages. Test-name or import inventories alone are not semantic coverage. Preserve the production page-size validation, ownership assertions and original failed evidence; do not fix this by tolerating malformed native pages.

Parameterized tests need a unique full name for every scenario. A status such as `completed` may describe several different cases, so include a distinct scenario label rather than only that shared status. Check the targeted runner's final evidence result, not just Vitest's passing assertions: duplicate case identities invalidate aggregation even when the assertions pass. Keep that failed evidence and rerun only the affected module after fixing the names.

History/sorting fixtures that create several independent operations must use distinct semantic scopes or finish the previous operation first. Reusing the same method and unresolved scope correctly trips duplicate-intent protection before the sorting assertion; fix the fixture rather than weakening that protection.

### Required review of every failed Reviewed checks run

Before submitting the next candidate, retain a failure review with the failed commit, run URL/ID, attempt, job IDs and complete-log evidence. Distinguish actual failed assertions from intentionally failing subprocess fixtures, upstream job failures and downstream jobs that correctly refuse incomplete evidence. Do not invent a test count or coverage result when the aggregation did not finish.

For each distinct cause, record:

1. What failed and the evidence establishing the cause. Separate a product defect, an invalid fixture, an environment mismatch and an external failure; mark an unconfirmed explanation as unconfirmed.
2. Why the previous affected-test selection, review or preflight missed it.
3. The repair and the search for analogous callers, fixtures and supported environments.
4. A concrete prevention measure, such as a regression assertion, a broader affected-test selection or an explicit preflight rule. "Be more careful" and "rerun CI" are not prevention measures.
5. The exact targeted verification, untested platforms/integrations and the next candidate's eventual CI result. Keep the original failed run and its evidence even after the repair passes.

Before choosing affected tests, consult the retained reviews and the rules below. Preserve expected behavior, privilege boundaries, recovery assertions and platform coverage. Do not solve fixture failures by dropping cases, broadly mocking validation, increasing timeouts, adding arbitrary sleeps or retries, or suppressing a failed gate. Waiting for an evidenced protocol prerequisite, such as the pinned CLI's activation-key guard, must be tied to the observed protocol state and documented separately from timeout inflation. Reopen the source-bound audit/authorization when a repair changes its snapshot; rerun the authorized full matrix only after that gate is satisfied. These records belong in repository audit evidence; the user README should remain deployment and usage guidance.

### v2.3.2 candidate: missed fixture dependencies

The first independent-conversation-copy candidate (commit `historical-commit-089`, Reviewed checks run `41316151654`) exposed gaps in affected-test selection. Its Security checks passed, but its test matrix failed; it was not deployable. The coverage job correctly rejected failed Linux evidence. The repairs below change fixtures and strengthen independence assertions; they do not establish a Linux pass until the subsequent Linux run completes.

| Change that affected fixtures | Why it escaped earlier checks | Prevention before another candidate |
| --- | --- | --- |
| Native launch adds fixed Codex `-c` arguments | A lifecycle fixture launched Node with `-e`, so the appended `-c` became Node's conflicting `--check`; Windows job fixtures also asserted the obsolete argument list. | For launcher-argument changes, search every launcher caller and command wrapper. Run lifecycle and exact-argument/escaping tests, including Windows descendants and cleanup. Use a script file when the fake executable must accept arbitrary CLI arguments. Preserve delays, cleanup and quoting assertions. |
| Candidate installation now validates application capability metadata | Synthetic legacy packages lacked `app/package.json`; root-only verification also missed ordinary-UID ownership assumptions. | Trace archive, install, update, migration, recovery and journal fixture builders when package validation changes. Give synthetic packages explicit valid legacy metadata before sealing. Exercise affected ordinary/root pairs with real file ownership. Keep malformed-package and downgrade rejection tests. |
| Existing conversations filter models by their bound provider | A default-settings UI fixture supplied model IDs without the provider metadata now required by the real response contract. | For a filtering/selection change, inspect all mock catalog, thread and session responses against the protocol. Test defaults, inherited selection and outgoing model/effort together, including loading and missing metadata; do not remove the filter just to satisfy an incomplete fixture. |
| Failed upstream test jobs reach coverage aggregation | A downstream red check can be mistaken for another product or coverage defect. | Read the complete upstream job results first. Preserve coverage's refusal of missing or failed inputs; report incomplete deduplication/coverage as unavailable, never as zero gaps. |

The detailed retained CI1 review binds the complete job logs, API results, repair evidence and limitations. Subsequent failures must add their own review and update these rules when they reveal another reusable cause; this table is not a substitute for reviewing each run.

The next candidate (`historical-commit-083`, Reviewed checks run `41318007104`) exposed a composed-fixture dependency missed in that repair. The ordinary installation fixture replaced `release_accounts` with a token-only result; the root account-recovery suite calls that fixture's `setUp()` and reuses its manager. Restoring only `verify_release` left the account check replaced, so two real downgrade assertions failed. This was a fixture regression, not evidence that production allowed an authentication downgrade.

When changing a shared fixture, search imports, direct instantiation, `setUp()` calls, method rebinding and cleanup as well as class inheritance. Keep real boundary readers in consumers that exercise those boundaries, and run the affected ordinary and root consumers under their actual identities. The selector now groups installation recovery, root release reuse and root account recovery bidirectionally; its regression requires the exact group and refuses a missing companion. Preserve the failed run and original downgrade assertions; targeted results do not replace the next candidate's full CI.

v2.2.0's failures fell into distinct categories. Ordinary-user deployment fixtures incorrectly assumed root ownership or mocked `chown` when the implementation used `fchown`; malformed saved profiles no longer represented valid inputs. Several UI tests waited for visible text while preview consent, IndexedDB acceptance or a later operation-list read was still pending. Fix those with controlled promises, awaited `act`, actual enabled-state/fresh-consent assertions, and completion of the real mutation promise—not sleeps, retries, global timeout increases or relaxed assertions.

An automation interruption also exposed a real runtime history/lifecycle consistency gap; the exact hosted interleaving was not reproduced. Windows native worker crashes prompted alignment with the already pinned deployment Node runtime; upstream fixes were verified, but no crash dump established the exact historical cause. Preserve those distinctions when diagnosing a new red run.

A full PR run and a selected push run can differ: in v2.2.0 CI10, the complete 232-file/2468-case run passed while three cases failed in the separately selected run. Keep that historical failure; do not reinterpret it as success. The new trigger policy deliberately avoids paying for both topic matrices, while retaining every test in an authorized full PR run and retaining main/manual validation. Fewer duplicate runs are not permission to weaken test readiness or release gates.

For deployment changes, verify the entire supported old-state upgrade and recovery sequence in an isolated fixture. Legacy sudo and shared lock-mode incompatibilities were discovered after earlier full CI passes. Manual permission changes on the real server cannot stand in for a product migration test. Unknown mutations retain their original IDs; inspecting a receipt never authorizes replay.

### CLI 0.169 upgrade lessons from local targeted validation

These are local v2.4.0 findings, not additional historical GitHub failures. Regenerating schemas alone did not catch the strengthened native provider lock: a conversion target created under the source provider could no longer resume under the target provider. Create the independent target with its final provider from the outset, preserve its native identity/header when copying, and leave the source history unchanged. Every CLI upgrade must run the actual provider-switch consumer, including compacted history, source-byte preservation, source deletion/restart, and attachment inheritance/reclamation; a generic smoke connection is insufficient. The 0.169 local fixture exercises loopback endpoints only and establishes no paid-provider acceptance.

Do not assert old numeric PIDs remain absent after restarting native processes or running fixtures in parallel: the OS can reuse them. Bind cleanup assertions to the specific spawned child and its close/exit proof. Keep real descendant-cleanup checks as separate evidence. When testing post-delete attachment reclamation, use the product deletion entrypoint, whose positive acknowledgement releases references; a raw CLI request can acknowledge before its asynchronous notification reaches the product. Preserve unknown-outcome retention and verify remaining fork/conversion references before expecting physical deletion.

### v2.4.0 full-audit findings before release

These are findings from the local full audit, not GitHub check failures. A repair in one layer must be checked through its actual consumers: keeping two receipt-export snapshots in the ledger did not fix a gateway that still kept only one export lease. Exercise two independent connections through the gateway, including disconnect, expiry and rotation, rather than relying only on the underlying storage test. Likewise, settings-draft protection must cover internal navigation and project-scope changes as well as the modal close button.

For bounded persisted JSON, check the exact final UTF-8 bytes, including formatting, the trailing newline and every wrapper, before any filesystem or service mutation. An individually valid request or a compact public summary does not prove the combined private settings or saved profile will fit its reader's limit. Test both multi-provider aggregation and profile-wrapper boundary expansion.

For pinned-tool upgrades, an existing cache's self-consistent manifest is insufficient: its identity must match the current expected versions, architecture and verified upstream distributions. An unchanged cached CLI can pass tree validation and then fail the final candidate probe only after an expensive build. Test an actual old-pin to new-pin cache transition, interrupted publication and tampering without replacing the previous usable generation.

The Windows preflight itself must obey the same process-ownership rule as production and fixtures: cleanup proof comes from the bound controller and kernel Job Object, with the standalone controller's authenticated exit message where applicable. Never probe or terminate a historical numeric PID after that proof; it may already name another process. A missing or failed proof remains a failure.

Round two also exposed a cross-layer authentication regression: changing invalid MFA to a distinct HTTP 401 error passed backend checks, but the real browser API interpreted that code as expired external authentication. Check login retries and authenticated security actions through the actual frontend API with the server's status, error code and delivery state. Component tests that replace the API with a successful mock cannot establish that contract. Preserve the known MFA stage, clear rejected secrets, and distinguish invalid proof from an expired session or an unknown mutation result.

Budget changes need consumer-side boundary checks as well as gateway tests. For browser events, verify legal payloads above the former limit, the exact shared maximum, and multibyte UTF-8 that exceeds the byte budget while its string length remains below it. A rejected event must expose recovery and permit fresh state without replaying business operations.

Settings protection must include replacing the selected object inside a panel, not only leaving the panel. Trace child editor remounts, saved revision changes, MCP server selection and shared-plugin selection; a parent's clean state does not prove its nested editors are clean. Migration flags likewise need validation of their resolved value, including inherited values: a public-to-internal TLS change must not retain public-only HSTS merely because the new command omitted the optional flag.

POSIX cleanup has the same identity requirement as Windows cleanup. A reaped group leader no longer reserves its numeric process-group identifier; subsequent group signaling can target a reused identity. Keep a bound leader or controller until descendant cleanup is confirmed, and use pidfds or captured process identities for fixture assertions. A no-signaling probe can establish reachability of an unsafe call; do not describe that as an observed real-world mis-kill.

The expanded MCP regression selection also found two stale expectations for raw English transport errors after the API's user-facing error contract changed. Trace the catch boundary before changing assertions: a thrown fetch failure is an unknown outcome, while a structured known-not-sent RPC failure must keep its delivery classification. Retain ownership, draft preservation and no-replay assertions while checking safe error text. Bind each verification claim to a log that actually contains that module/case; a broad list of earlier passing logs is not evidence for a test that those runs never selected.

Round three found that a correct dedicated-process cleanup implementation does not guarantee its caller handles failed cleanup. Account probes must publish results and caches only after confirmed cleanup, recheck account generation and runtime availability after every await, and retain uncertain cleanup in the service's ownership set. A successful read followed by failed cleanup is still an uncertain runtime. Test concurrent reads, account changes during cleanup, whole-service shutdown, failed cleanup after a failed read, and cache consumers through the real service; preserve legitimate CLI-owned account reads.

Preserving a settings draft also means preserving its target. If another browser or profile replacement deletes the selected provider, a fallback to the default summary can silently redirect that draft. Verify the actual API request identity through removal and profile replacement, keep the missing target explicit, and disable its mutations until the user selects a valid target. Never infer legacy single-provider mode merely from a missing field in a fallback object.

### v2.4.0 first local full matrix

The first candidate's local full matrix exposed failures before any push or hosted check. Keep its original Windows/Linux reports and raw Vitest results; a failed JavaScript group does not contain successful case reconciliation, and passing deployment/Go groups do not make the matrix pass. Do not relabel these local failures as historical GitHub failures.

After lazy loading, the settings fallback and the real settings panel can be different dialog elements. Wait for the actual target control before capturing its dialog or triggering access expiry; waiting inside a detached fallback container cannot establish readiness. After API error redaction or no-op configuration filtering changes, run their actual consumers: assert the safe transport error and delivery classification, and distinguish undoing an unsaved edit from clearing a persisted value. Both absence of an unnecessary RPC and the genuine clearing mutation need coverage. Date assertions must use the product's explicit locale instead of the test host's default.

An initial asynchronous default selection must not overwrite a newer explicit user selection. Preserve a first-render interaction regression that clicks a real newly visible control while the first resource response is settling. A later isolated pass does not disprove the failed full-matrix interleaving.

Keep integration tests bounded by avoiding repeated unrelated setup within one assertion group. The emitted-artifact test exceeded its existing deadline while running four complete Git/source/authorization/preflight sequences. Retain one complete real preflight/build, then exercise the real artifact validator for changed, additional and missing artifacts. Preserve all refusal assertions and separate full-preflight integration coverage; do not raise the timeout, lower concurrency or add retries to conceal the repeated work.

The second local matrix exposed the same unnecessary repetition in the failed-rebuild case. Fixing only the first timed-out case was incomplete: inspect every call to the expensive full entrypoint in the entire module, including tests that narrowly passed. Keep complete preflight coverage for the initial build, evidence-only new-commit reuse, authorization and commit/target validation. Exercise artifact reuse, failed rebuild cleanup, missing records and source changes during a real build through the actual `checkBuild` boundary, with real build commands and committed-source verification. Preserve every refusal and publication assertion. A targeted pass alone does not establish the next full matrix's timing or correctness; retain both failed candidates and verify the next unchanged candidate across all platforms.

Round three found that a stale repository approval checksum could override a valid committed release authorization on the next main push. Keep trust sources separate: repository approval is only a PR approval source, trusted main validates the committed source-bound authorization, and a manual run's explicitly supplied checksum must still match exactly. Test the real Git-backed planner for all three event paths, including PR self-approval rejection and stale source bytes; a selected-test plan or workflow text check alone does not exercise this boundary.

Round four checked the missing-file branch of that same contract: an explicitly supplied checksum must require its authorization file even for a narrow change. Optional PR approval without a file may still select ordinary affected tests, but never authorize a broad scope. Exercise file absence as well as invalid and stale contents; validating only an existing file leaves the explicit-request failure path untested.

# v2.3.3 本地修复验证记录

本记录区分本地定向测试失败与 GitHub `Reviewed checks` 失败；以下事项发生在提交候选前，不计为新的 GitHub 失败。后续 CI 的实际结果另行记录，旧失败产物不覆盖。

## 遍历 API 的平台差异

新打包回归最初只拦截 `os.scandir`，但本机 Python 3.12 的 `Path.iterdir()` 使用 `os.listdir`，因此“已经观察到遍历”的断言失败。生产实现没有进入被排除目录；失败说明夹具未观察到真实调用路径。

修复同时观察两个枚举 API，保留“被排除目录绝不能被访问”、允许文件内容完整、输出不能落入输入树和旧归档不被覆盖的断言。预防规则是根据支持的 Python 版本检查标准库实现差异，不把一个内部枚举函数当作稳定公共接口。原失败保留于 `.work/v233-audit-1/source-pack-fixture-failure.log`；修复后的部署定向结果为 109 项中 102 通过、7 项待 Linux 验证，没有把跳过计为通过。

## 未知活动与断开连接是不同状态

只读媒体授权回归最初调用 `dispatcher.disconnected()` 模拟活动未知，实际同时撤销了连接租约，因而没有抵达要验证的只读准入分支。修复以已连接运行时加 `activity.unknown=true` 建立准确前提，保留“未知活动时仍允许已授权的只读媒体、执行变更仍受阻”的断言。

预防规则是分别建立传输连接、执行租约和业务活动状态，不用断开连接代替所有不确定状态。原失败产物为 `.work/test-results/run-i708IA`，对应 14 项修复回归保留于 `.work/test-results/run-InNGBk`。网关独立恢复入口与回执容量定向验证的 9 文件 115 项结果保留于 `.work/test-results/run-5IZDM7`；这些集合可能重叠，不相加为完整覆盖数。

## 生成图片的原生扩展与旧 ResponseItem 不等价

一次真实 CLI 回环夹具直接向 Responses 流注入旧 `image_generation_call`。Codex 0.164 将它记录到 rollout，但没有将其作为真实生图扩展的完成条目加入公开历史索引，因此该夹具不能证明真实扩展的端到端行为。保留失败于 `.work/test-results/run-gBVqJ4`，撤下不成立的夹具，不将撤下当作成功测试。

随后沿固定上游源码核对实际 `ExtensionItem::ImageGeneration` 到公开 `ThreadItem::ImageGeneration` 的转换。预防规则是先建立扩展事件、公开通知和持久历史的真实路径，再设计协议替身；公开协议回归、真实浏览器图片下载和商业生图调用是不同证据，不互相替代。

## 大媒体读取的旁路消费者

逐条读取历史的改造之外，转换副本完成后的校验仍直接读取整个回合。这是独立终审发现的真实遗漏：多张各自合法的图片合并后仍可能超过原生单帧预算。最终校验只需已复制会话的元数据，改用有界视图，并保留复制、原会话不变和独立身份的原有验证。预防规则是搜索所有直接原生历史调用，区分需要完整内容的使用者与只需状态的校验，不只检查面向网页的历史入口。此发现使第一份冻结候选不能作为全局清洁轮；修复后重新冻结并复核。

## 固定默认值不等于原生自动忽略旧值

第二份冻结候选的交叉复核发现：目录列出固定默认强度、可调列表为空时，真实 CLI 仍会使用旧回合的强度。回环实测同时观察协作模式和普通回合的实际出站请求：协作模式中的 null 会选目标默认，但普通回合省略 effort 或传顶层 null 都仍沿用旧值；显式提交目录已知默认才一致生效。

因此选择固定强度模型时采用目录明确的默认值，界面仍不开放任意档位；校验只额外接受与唯一目标模型固定默认精确一致的值。未知默认和合法继承保持原语义。预防规则是将目录、选项控件、请求构造与真实出站值一起验证，不能把“没有可调列表”推断成“原生会忽略所有覆盖值”。真实回归保留于 `.work/test-results/run-v4qYut`，不包含商业调用。第二份冻结候选也不能被标为全局清洁轮。

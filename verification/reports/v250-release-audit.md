## 验收边界

- 手机端区分自动化交互、真实浏览器事件和用户先前报告的真机现象。本文没有把模拟测试计作一次新的手机 Edge 真机验收。
- 使用官方 Codex CLI 核对 479 个 JSON 与 951 个 TypeScript 协议生成文件。以公开资料核验智谱四个内置服务，实际工具传输走隔离的本地环境。外部商业服务的成功率、会员权限与当时偶发失败的唯一根因仍无法从这些测试推定。
- 原生传输每帧最多 12 MiB。单条非图片消息已经超过此值且独立时间线也不能返回可用游标时，应用仍须遵守这条传输边界。
- 隔离 Debian 的用户、项目、自动化、回执与系统服务用于升级验证。发布到 GitHub 与升级用户线上实例是两个独立动作。

## Debian 的实际升级结果

专用 Debian 12 实例上先从原版 v2.4.0 运行真实应用，完成管理员登录，建立浏览器 WebSocket，创建项目与暂停的自动化，记录两条已接受的操作回执。旧控制程序因服务启动问题需要先升级，建立业务基线时复用了经原版校验并封存的 v2.4.0 应用包。

随后使用正式管理入口依次完成控制工具升级、配置迁移、HTTPS 配置核对、应用升级和安装验证。升级后原浏览器 cookie 仍有效，原管理员可重新登录，WebSocket 可用，能按原 ID 读取项目与暂停的自动化，两条回执仍为 accepted。SQLite 完整性检查通过，运行表由 16 列迁为 17 列。随后对 17 列账本执行正常停服恢复并重启，再次确认原 cookie、项目、自动化和两条已接受回执均有效。独立 Linux root 控制工具和账本恢复定向测试 76 项全部通过。另一次更新实际安装了长会话修复，用 10,073,992 字符输入得到 988,500 字符的展示窗口，最新最终答复保留。[升级证据](../audit-evidence/v250-platform/debian-upgrade.json)

## 第六、七轮复审

第六轮在修订排序后覆盖 2,182 个文件，执行 172 个定向用例、1,200 组排序比较，重建并比对 1,430 份官方协议文件，未发现新增需修问题。[第六轮独立记录](../audit-evidence/v250-round6/independent.json)

第七轮核对同份源码，在两个真实的智谱配置管理流程中分别复现 P2 缺陷。第一项是连接切换后，服务显示名称从带连接后缀变成无后缀，原本属于同一连接的强制启用、停用均失效。第二项是永久删除连接后，其开关仍占据 128 项存储额度。顺次创建并删除 32 条各有四项开关的连接后，新连接显示没有覆盖设置，用户却无法再保存第一个开关。两项均能通过本地正式入口重现。外部智谱调用并非触发条件，本次复现也无法推断此前某次服务调用失败的原因。[第七轮独立记录](../audit-evidence/v250-round7/independent.json) · [连接切换](../audit-evidence/v250-round7/provider-switch.json) · [额度耗尽](../audit-evidence/v250-round7/removed-provider-capacity.json)

修复后，每个内置服务的开关跟随连接的固定编号和服务种类。旧格式的带后缀、无后缀设置会迁移至同一稳定记录。管理器为两个运行身份提供只含编号的清单，暂时停用、有配置档案可恢复及事务仍可回滚的连接继续保留。确认永久删除的记录可由各运行身份在自己的私有存储中回收，既有满额度存储也能再次保存。在多连接界面，默认关闭说明根据实际受管的服务定义展示。使用正式管理入口重放 32 次增删、双连接切换、普通及特权用户目录、配置档案恢复和候选健康检查失败回退；97 个 Python 定向用例及 77 个网页与运行时相关用例通过。

## 第九轮和原配置的连续启动验收

两种合法的 TOML 写法触发同一项启动缺陷。一种用点号键为服务赋内联表，另一种在表头的双引号名称内使用 Unicode 转义。Python 可以把两种写法解析成正确的服务和开关值。旧迁移代码仍按文本拼写查找待删除的设置，写入待确认区后无法移除原设置，后续启动反复失败。

在原始配置的副本上分别以 Debian 普通服务身份和 root 运行正式启动器，每例在同一 HOME 连续启动两次。修复前异常写法的八次启动全部失败，规范表头的四次对照成功。修复后十二次均收到官方 Codex CLI 0.169.0 的初始化响应。原模型设置保留，旧开关保存在待确认区，没有指向其他连接；每组第二次启动前后两份持久文件的内容、inode、权限和修改时间均一致。另对点号键、引号、内联表及相邻字段的 216 种组合做了定向验证。[原配置](../audit-evidence/v250-round9/original-config-retries.json) · [实际启动记录](../audit-evidence/v250-platform/toml-startup.json)

## 第十轮复审

对第九轮修复后的 2,183 个源文件重新审阅，119 项 TypeScript 与 103 项 Python 定向用例通过。上一轮两份原始故障配置和规范对照再次通过连续启动验证。另有一项新的 P1 兼容性问题。固定的官方 CLI 支持配置文件起始的 UTF-8 BOM、内联表的尾逗号和多行内联表。用户仅定义一个普通自有 MCP 服务，未设置旧开关，也会在正式托管启动器检查认证存储时被 Python TOML 读取器拒绝。即使越过该入口，旧的 MCP 开关读取器仍会拒绝同一份配置。

专用 Debian 上使用同一份 Codex CLI 0.169.0、两种账户和四份配置，每份各冷启动两次。直接运行 CLI 的 16 次均完成初始化。走托管入口时，三份特殊写法的 12 次启动全部失败，规范对照的 4 次成功。失败时文件保持原样。最初官方来源因网络中断暂时不可达，复审结束前已成功取得全部六项来源。第十轮有新发现，未计入连续清洁轮次。[独立审阅](../audit-evidence/v250-round10/independent.json) · [同一 CLI 的握手对照](../audit-evidence/v250-round10/format-handshake.json) · [认证存储入口](../audit-evidence/v250-round10/format-storage-precheck.json)

### 第十一轮补充核实

另核实一项低频 P3。若已有服务名称恰好包含系统会隐藏的配置值，浏览器显示替换后的名称；旧页面直接用该显示名请求编辑或移除，找不到原服务。用普通合成词和停用的本地服务验证，即使提供当前配置版本，移除和只保存开关都失败，原文件未变。高熵密钥与日常服务名偶然重合的概率低，但命中后用户确实失去该条配置的管理能力。此项在正式审阅结束后另行核实，保留其真实发现时间。[补充复现](../audit-evidence/v250-round11/masked-name-followup.json)

### 第十一轮修复和验收

网页分别跟踪地址、程序、参数与敏感字段的实际编辑，停用服务只提交开关。用户可明确替换或清空整组参数，撤销后恢复原编辑意图。在固定 CLI 上执行七次真实配置保存，逐项核对隐藏字段仍存于私有配置，明确修改的字段按请求变化。[三组实际保存](../audit-evidence/v250-round11/masked-form-acceptance.json)

服务端在当前运行身份的用户目录校验原文件版本，局部编辑 TOML，核对完整语义，再让官方 CLI 重新读取与加载。未编辑服务、维护注释、原生日期类型、BOM、CRLF 及原有 TOML 1.0 兼容性均有回归。覆盖新增、传输转换、移除、重新创建以及带点号、引号和中文的名称。提交前失败可确认未写入，替换文件后同步或读回失败会明确标为结果未知。未更新控制工具的部署在写入前提示先更新。另对 400 项名称、写法、换行及字段编辑组合验证了持久数据和重复操作。

服务配置的显示名与操作标识分开。即使两个服务的显示名同时被隐藏成相同文字，也按用户选择的行编辑及移除。版本过时、后台重启导致标识失效时，操作会要求重选。两项停用的本地服务经生产表单和固定 CLI 读写验证，目标服务有变更，另一项保持原样。[同名显示的实际验收](../audit-evidence/v250-round11/masked-config-identity.json)
